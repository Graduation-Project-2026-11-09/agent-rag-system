# AI の構成（Agentic RAG）

> **このドキュメントは一部未定。** 計画書（プロジェクト計画書）に書かれた方針をまとめたもの。「未定」の項目は、決まりしだい更新する。

## 方針（計画書より）
- 一般的な RAG に AI エージェントの機能を組み合わせた **Agentic RAG** を採用する
- 回答には**必ず根拠資料を表示**する。根拠が見つからない場合は推測で答えず、担当部署への問い合わせを提案する
- AI は**自動で送信・申請しない**。問い合わせは利用者が確認・承認してから送る
- 通常の RAG と Agentic RAG を**切り替えられるようにし**、同じ質問で「必要な情報を取得できた割合・回答の正確性・回答時間・料金」を比較する
- 開発・検証では**ダミー資料だけ**を使う（外部の AI に本物の社内資料を送らない）

## エージェント
### 検索Agent
質問を分析し、どの資料を・どんな言葉で検索するかを判断する。

```
質問
 │
 ▼
① 質問分析 ─── 何を調べればよいか（観点）を洗い出す
 │              例:「結婚した」→ 氏名変更・扶養・社会保険・慶弔制度
 ▼
② 検索語の展開 ─ 利用者の言葉を、社内資料の正式な言葉に言い換える
 │
 ▼
③ 検索 ─────── pgvector でベクトル検索（利用者が見られる資料だけ）
 │
 ▼
④ 充足度の評価 ─ 回答に必要な情報がそろったか判断する
 │      │
 │      └─ 足りない → 条件を変えて ②へ（再検索は最大 3 回）
 ▼
⑤ 回答の作成 ─── 観点ごとに整理し、根拠資料の番号を付ける
                  次に行う手続きを、期限・担当部署つきのチェックリストにする
```
①〜④の過程は画面にリアルタイムで表示する（質問送信から 3 秒以内に表示を開始する）。

### 業務支援Agent
資料だけでは解決できない場合に、次の行動を提案する。
- 「担当部署への問い合わせを作成しますか？」と提案する
- 会話の内容・確認済みの資料・不明点から、宛先部署・件名・本文の下書きを作る
- 利用者が編集し、「承認して送信」を押したときだけ送信する

## 資料の取り込み（worker）
```
アップロード → S3 に原本を保存
   → テキスト抽出 → チャンク分割 → ベクトル化（OpenAI）→ pgvector に保存
   → 検索可能になる
```
- まず PDF・Word・テキストに対応する。Excel・PowerPoint はその後
- 読み取れない資料はエラーの理由を表示し、取り込み直せるようにする
- 資料ごとに公開範囲（全員 / 部署限定）を持ち、検索のときに絞り込む
- 改定した場合は新しい版で検索する（古い版は履歴として残す）

## 目標値（計画書より・案）
| 項目 | 目標 |
|---|---|
| 検索過程の表示開始 | 質問送信から 3 秒以内 |
| 回答完了 | 再検索を含めて平均 30 秒以内 |
| 同時利用 | 50 名程度 |

## 使用するモデル（2026-11-09 決定）
すべて OpenAI API。料金は公式の Standard 料金（100 万トークンあたり、2026-11-09 時点）。

| 役割 | モデル | 料金（入力 / 出力） | 理由 |
|---|---|---|---|
| ① 質問分析・② 検索語の展開 | `gpt-6-luna` | $0.10 / $0.50 | 決まった形（JSON）の出力で、速さが大事（3 秒以内に検索過程を表示） |
| ④ 充足度の評価 | `gpt-6-luna` | 同上 | 「足りる・足りない」の判断。1 回の質問で最大 4 回呼ぶ |
| ⑤ 回答の作成 | `gpt-6-luna` | 同上 | 費用を最優先。品質が足りなければ `gpt-6.1-terra`（$1.00 / $5.00）に変える |
| 問い合わせ文の下書き | `gpt-6-luna` | 同上 | 同上 |
| 資料・検索語のベクトル化 | `text-embedding-3-large` | $0.13 | 検索の精度を優先（3072 次元。DB は `halfvec(3072)`） |

- モデル名は環境変数で切り替える: `OPENAI_CHAT_MODEL_FAST`（①②④）、`OPENAI_CHAT_MODEL_ANSWER`（⑤・下書き）、`OPENAI_EMBEDDING_MODEL`。使ったモデルは `agent_runs.config` に記録する
- 応答を速くするため、luna の推論の深さ（reasoning effort）は `none` か `low` から試す
- 費用の目安: 質問 1 回 約 $0.0023（約 0.3 円）、月 1,000 問で約 $2.3。資料 300 件のベクトル化は 1 回 約 $2.3
- gpt-4o・gpt-4.1・gpt-5-mini などは OpenAI が廃止を予定しているので使わない
- 評価（[db.md 4.9](db.md#49-評価通常の-rag-と-agentic-rag-の比較)）で、回答の作成を luna と terra で比べ、品質が足りなければ terra に変える

## Agent の設計（2026-11-09 決定）

### 構成：コードの決まった流れ ＋ その中で AI がツールを選ぶ
外側の流れ（順番・回数・時間・費用の上限・記録・画面表示）は**コードで固定**し、検索の段階だけ **AI がツールを選んで使う**。AI に自由を与えるのは「何をどう調べるか」だけで、「いつ止めるか」「何をしてよいか」はコードが決める。

```
質問
 │
 ├─ 段階1 分析（コードが呼ぶ・1 回）
 │    観点の洗い出しと、質問の種類の判定（Structured Outputs で JSON を受け取る）
 │
 ├─ 段階2 検索ループ（AI がツールを選ぶ）
 │    AI: 「search_documents を この検索語で」→ コード: 上限を確認して実行 → 結果を AI に返す
 │    AI が finish_search を呼ぶか、上限に達したら終わり
 │
 ├─ 段階3 充足度の判定（コードが呼ぶ・1 回）
 │    観点ごとに「根拠があるか」を、チャンクの番号つきで判定 → コードが根拠を検証
 │
 └─ 段階4 回答の作成、または問い合わせの提案（コードが呼ぶ・1 回）
```

実装は自作（Python）。OpenAI API の function calling で、段階2 のツールを AI に選ばせる。各段階の結果は画面に送り（SSE）、`agent_runs.steps` に記録する。

### 段階2 で AI が使えるツール
すべて**読み取り専用**。問い合わせの送信やデータの変更ができるツールは作らない（AI が自動で送信しない、という要件を仕組みで守る）。

| ツール | 内容 |
|---|---|
| `search_documents(queries, aspect)` | 検索語（最大 5 個）をベクトル化して検索し、上位のチャンクを返す。どの観点のための検索かも渡す |
| `get_neighbor_chunks(chunk_id)` | 見つかったチャンクの前後を読む（表や手順が途中で切れているとき） |
| `get_document_outline(document_id)` | 資料の見出しの一覧を見る（どの章を探せばよいか判断するため） |
| `finish_search(reason)` | 検索を終える |

- **公開範囲はツールの中で必ず絞り込む**。利用者・部署は AI からは受け取らず、ログイン中の利用者からコードが決める（AI が他部署の資料を探すことはできない）
- 資料の本文に「この指示に従え」などの文が入っていても、ツールは読み取りしかできないので、被害が広がらない。本文は「資料のデータ」として AI に渡し、指示として扱わないようプロンプトにも書く

### 制限（コードで強制する）
| 項目 | 上限 | 上限に達したら |
|---|---|---|
| `search_documents` の回数 | 4 回（初回 ＋ 再検索 3 回。計画書のとおり） | 段階3 に進む |
| ツールの呼び出し回数の合計 | 8 回 | 段階3 に進む |
| 1 回の検索の検索語 | 5 個 | 6 個目以降は使わない |
| AI に渡すチャンク | 合計 20 件（約 8,000 トークン） | 類似度の低いものから外す |
| 検索ループの時間 | 20 秒 | 段階3 に進む（目標: 回答完了まで平均 30 秒） |
| 1 回の質問で使うトークン | 入力 合計 40,000 | 段階3 に進む |
| 同じ検索語の繰り返し | 禁止 | 検索せずに「同じ検索語です」と AI に返す |
| 新しいチャンクが見つからない検索 | 2 回続いたら | 段階3 に進む |
| 存在しないツール・形式の違う引数 | 実行しない | 回数に数えてエラーを AI に返す |

### 問い合わせを提案するかの判断
#### 判定の種類（段階3 の出力）
| 判定 | 例 | 回答 | 問い合わせの提案 |
|---|---|---|---|
| `answered` | 結婚の手続き（すべての観点に根拠あり） | する | しない |
| `partial` | 一部の観点だけ資料にある | 根拠のある部分だけ回答 | する（足りない観点について） |
| `needs_individual_judgment` | 「私の場合、時短勤務を延長できる？」 | 一般的なルールだけ回答 | する（個別の判断は担当部署が行うため） |
| `no_evidence` | 資料にまったく書かれていない | **推測で回答しない** | する |
| `out_of_scope` | 天気・雑談など、社内の制度と関係ない | 対象外と伝える | しない（担当部署に無関係な問い合わせを送らない） |

#### 精度を上げる仕組み
1. **根拠のない「足りている」を認めない**: 段階3 で「この観点は足りている」と答えるときは、根拠のチャンクの番号を必ず付けさせる。コードが、その番号が実際に検索で見つかったもので、類似度が基準以上かを確かめる。確かめられない観点は「足りない」として扱う
2. **数値でも判定する**: 一番近いチャンクの類似度が下限より低ければ、AI の判定にかかわらず `no_evidence` にする（下限は評価で決める）
3. **宛先の部署**: 根拠や近いチャンクの資料の管理部署と、AI の判定を合わせて決める。部署マスタにない部署は使わない
4. **迷ったら提案する側に倒す**: 推測で答えるほうが、提案しすぎるより害が大きい（計画書のリスク対策①）。提案はあくまで提案で、送るかどうかは利用者が決める

#### 精度の測り方
- **評価用の質問**（[db.md 4.9](db.md#49-評価通常の-rag-と-agentic-rag-の比較)）に、正しい判定と正しい宛先の部署を付けておき、AI の判定と比べる
  - 「問い合わせるべき質問」を見逃さない割合（再現率）: 目標 90% 以上
  - 提案したうち、本当に問い合わせが必要だった割合（適合率）: 目標 80% 以上
  - 宛先の部署の正解率
- **実際の利用からも確かめる**（利用履歴の画面で見る）
  - 提案したのに「今回は不要」が押された → 提案しすぎの可能性
  - `answered` と判定したのに、低評価や、そのあと問い合わせが送られた → 見逃しの可能性
- 結果を見て、類似度の下限とプロンプトを調整する。調整した内容は `agent_runs.config` の `promptVersion` で区別する

## 費用の対策
- 再検索の回数に上限（3 回）を設ける
- AI の利用量（トークン数）を記録し、利用履歴で確認できるようにする
- OpenAI の API キーに利用上限を設定する
