# PR の書き方とレビューの仕方

## PR を作る人

### 作る前に
- [ ] ローカルでテストとコードチェックが通る
  ```sh
  docker compose exec api pytest
  docker compose exec api ruff check . && docker compose exec api ruff format --check .
  docker compose exec frontend npm run lint
  ```
- [ ] 秘密情報（`.env`、API キー、本物の社内資料）が含まれていない
- [ ] 変更は1つの目的にまとまっている（目安: 差分 400 行以内。大きいときは分ける）

### PR に書くこと
PR を作るとテンプレート（`.github/pull_request_template.md`）が自動で入るので、埋める。

| 項目 | 書くこと |
|---|---|
| タイトル | [git-workflow.md](git-workflow.md) の形式（例: `feat(frontend): チャット画面を追加`） |
| 概要 | **何を・なぜ**変えたか。「なぜ」が一番大事 |
| 関連 Issue | `closes #12` と書くと、マージ時に Issue が自動で閉じる |
| 変更内容 | 主な変更点の箇条書き |
| 動作確認 | 何をどう確認したか。画面の変更はスクリーンショット |
| レビューしてほしい点 | 迷ったところ、自信がないところ |

### 作ったあと
1. CI が成功するのを待つ。失敗したら直す
2. CodeRabbit のコメントを確認する。対応したら Resolve、不要なら理由を返信して Resolve
3. **Enable auto-merge** を押しておくと、承認された時点で自動でマージされる
4. 作業途中で見てほしいときは **Draft** で作る（CodeRabbit も Draft ではレビューしない）

## レビューする人（リーダー・副リーダー）

- **どちらか1人が Approve すればマージできる**
- 自分の PR は自分で承認できないので、リーダーの PR は副リーダーが、副リーダーの PR はリーダーがレビューする
- 依頼されたら **24 時間以内（平日）** に一度は反応する

### 見るポイント
1. **目的**: PR の概要どおりの変更になっているか。仕様（設計書・Issue）と合っているか
2. **動作**: 正常系だけでなく、エラー・空の入力・権限がない場合を考えているか
3. **セキュリティ**: 権限チェック漏れ、資料の公開範囲の漏れ、秘密情報、SQL を文字列で組み立てていないか
4. **AI まわり**: 根拠のない回答をしない作りになっているか。AI が利用者の承認なしに送信・申請しないか
5. **テスト**: 変更に対するテストがあるか
6. **読みやすさ**: 命名とコメントが [coding-style.md](coding-style.md) に沿っているか

### コメントの書き方
頭に種類を付けて、必ず直すべきものか分かるようにする。

| 接頭辞 | 意味 |
|---|---|
| `[must]` | 直さないとマージできない |
| `[want]` | できれば直してほしい |
| `[nits]` | 細かい指摘。直さなくてもよい |
| `[ask]` | 質問。意図を知りたい |
| `[good]` | 良いところ |

例: `[must] 部署担当者が他部署の問い合わせを見られてしまいます。department_id で絞り込んでください`

人ではなくコードについて書く。「なぜ」を添える。

### 結果の付け方
| 結果 | 使うとき |
|---|---|
| **Approve** | `[must]` がない（`[want]` 以下は残っていてもよい） |
| **Request changes** | `[must]` がある |
| **Comment** | 質問だけ、または途中の確認 |

## CodeRabbit（AI レビュー）
- PR を作ると自動でレビューが付く（Draft を除く）
- **補助**として使う。指摘が間違っていることもあるので、鵜呑みにしない
- PR のコメントで `@coderabbitai` に質問できる（例: `@coderabbitai このクエリの性能は問題ない？`）
- CodeRabbit の承認はマージの条件に含まれない。必ず人が Approve する
