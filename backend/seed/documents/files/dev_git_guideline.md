# 開発部 ソースコード管理ガイドライン

株式会社サンプル 開発部（ダミー資料。開発部内のみ公開）
2026年5月1日版

## 1. リポジトリ

### 1.1 リポジトリの作成
業務のソースコードは、会社が契約した Git ホスティングサービスの組織アカウントで管理します。個人のアカウントにリポジトリを作ってはいけません。新しいリポジトリは、開発部のリーダーが作成します。

### 1.2 公開範囲
リポジトリは、すべて非公開（Private）にしてください。オープンソースとして公開する場合は、開発部長と情報システム部の承認が必要です。

## 2. ブランチ

### 2.1 ブランチの運用
- main ブランチは、常に本番に出せる状態に保ちます
- 作業は main から作った作業用ブランチで行います
- ブランチ名は「種類/課題番号-説明」とします（例：feat/123-login）

### 2.2 main への直接の push
main ブランチへの直接の push は禁止です。ブランチ保護で禁止しています。

## 3. コミット

### 3.1 コミットメッセージ
コミットメッセージは「種類: 何をしたか」の形で書きます。種類は feat（機能の追加）、fix（バグ修正）、docs（ドキュメント）、refactor（整理）、test（テスト）、chore（その他）です。

### 3.2 秘密情報
パスワード、API キー、証明書の秘密鍵などの秘密情報をコミットしてはいけません。誤ってコミットした場合は、すぐにキーを無効にして、情報システム部に報告してください。履歴から削除するだけでは不十分です。

## 4. プルリクエストとレビュー

### 4.1 レビューの必須化
main に取り込むには、プルリクエストを作り、1人以上のレビューで承認を受ける必要があります。自動テストが失敗している場合は取り込めません。

### 4.2 レビューの観点
- 仕様どおりに動くか
- テストが書かれているか
- 秘密情報や個人情報が含まれていないか
- 読みやすく、既存の書き方に合っているか

### 4.3 レビューの期限
レビューを依頼されたら、1営業日以内に対応してください。対応できない場合は、依頼者に連絡してください。

## 5. 依存パッケージ

### 5.1 追加するとき
外部のパッケージを追加するときは、ライセンスを確認してください。GPL など、ソースコードの公開が必要になるライセンスのパッケージを製品に含める場合は、開発部長の承認が必要です。

### 5.2 脆弱性
依存パッケージの脆弱性は、自動のチェックで毎日確認しています。重大な脆弱性が見つかった場合は、1週間以内に更新してください。

## 6. 生成 AI の利用
コーディング支援の生成 AI は、会社が契約したサービスだけを使えます（情報セキュリティポリシー第21条）。生成されたコードも、通常のコードと同じようにレビューしてください。
